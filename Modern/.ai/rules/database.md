# Database Rules

## Compatibility

- ERP SQL MUST be compatible with **Firebird 2.5**.
- Do not use SQL features introduced only in later Firebird versions.
- When Firebird 2.5 compatibility is uncertain, verify support before using the feature.
- SQLite is restricted to the existing SERPRO `calculadora.db` synchronization flow.
- Any other SQLite use requires developer consultation and explicit approval before design or implementation.
- Preserve the database engine established by the component being modified.

## Data Access

- Business, domain, and application code MUST NOT directly depend on concrete database libraries or components such as UniDAC, FireDAC, ZeosLib, `TFDQuery`, or `TUniQuery`.
- Runtime database access MUST use the infrastructure abstractions established by the project.
- Use `IDatabaseConnection` for database command execution and `ITransaction` for explicit transaction boundaries.
- Concrete database technologies belong to infrastructure implementations.

## Persistence SQL

- Persistence SQL for domain/application data SHOULD reside in the appropriate repository implementation.
- Business and domain components MUST NOT contain persistence SQL directly.
- Infrastructure components whose responsibility inherently requires SQL, such as synchronization or import components, are not required to be repositories.
- Do not introduce an ORM or query builder without an explicit architectural decision.

## Object Naming

For new database objects:

- Use `UPPER_SNAKE_CASE`.
- Table names MUST NOT use generic prefixes such as `TB_` or `TBL_`.
- New UUID-based primary key columns MUST use `CHAR(36) NOT NULL`.
- UUID primary-key values generated by a repository MUST use its inherited `GenerateNewUUID` helper by default.
- UUID values generated outside a repository MUST use `GuidService.New` by default.
- Modern-generated UUID values MUST be represented as 36 characters without braces.
- A legacy column named `UUID` or `GUID` is not evidence of a valid Modern convention; determine its actual role and contract before using it as precedent.
- Do not rename legacy objects solely to enforce current conventions.

## Transactions

- Transaction boundaries belong to the Application / Use Case layer and MUST use `ITransaction`.
- Repository methods MUST use the active transaction and MUST NOT independently begin, commit, or rollback by default.
- A repository MAY own a transaction only for an explicitly designed isolated auto-commit operation.
- Existing repositories that own transactions are legacy behavior and MUST NOT be used as precedent for new code.
- The transaction owner MUST call `Commit` explicitly when the operation succeeds, even when the implementation also commits automatically on database disconnection.
- Do not split a logically atomic use case into independent transactions merely to simplify implementation.

## Synchronization and Import

- Treat identifiers maintained by external authoritative sources as externally owned data.
- Preserve source identifiers by default; do not replace them with generated UUIDs without an explicit, approved mapping requirement.
- Tables that mirror data maintained by the official SERPRO calculator MUST be
  populated and maintained through the established external synchronization flow.
  Migration SQL MAY create or alter their schema, but MUST NOT use `INSERT`,
  `UPDATE`, or `DELETE` to seed or maintain their mirrored rows.
- Data-manipulation statements found in the official calculator migrations are
  evidence of source-data evolution. They MUST NOT be copied into ERP migrations
  for mirror tables; the corresponding effect belongs to synchronization.
- A connection to an external database MUST be created through `IDatabaseConnectionFactory`.
- File and service sources MUST use an adapter appropriate to their format or protocol.
- Reader and Writer Ports are the preferred boundary for new synchronization and import flows. A simpler boundary MAY be used when the operation is small and the approved design does not benefit from separate Ports.
- The ERP Writer MUST use the operational Firebird connection and the active Use Case transaction.

## SQL Safety

- Runtime data values MUST use SQL parameters through `IDatabaseConnection`.
- NEVER concatenate user-controlled or runtime data values directly into SQL.
- Dynamic identifiers MUST come from trusted/validated allowed values and be kept to the minimum necessary.

## Query Changes

- Prefer explicit column lists over `SELECT *` in new persistence queries.
- Select only the columns required by the operation.
- Preserve existing query semantics and result shape unless the task explicitly requires changing them.
- Do not rewrite working legacy SQL solely for formatting or modernization.
- Make performance changes only when required by the task or supported by an identified problem.

## Schema Safety

- Do not create, alter, rename, or drop database objects unless the task explicitly requires a schema change.
- Verify existing object and column names from the repository whenever possible; do not invent schema objects.
- Destructive schema changes require explicit need and consideration of existing data and deployed installations.

## Migration History

The project uses a custom database migration mechanism.

- Released migration history is immutable: NEVER delete, reorder, or rewrite released commands.
- New migration commands MUST be appended according to the project's migration process.
- Do not modernize historical migration commands to comply with current conventions.
- Current standards apply to newly introduced objects and commands unless compatibility requires otherwise.
- Detailed migration procedures belong to the `database-migration` skill.
